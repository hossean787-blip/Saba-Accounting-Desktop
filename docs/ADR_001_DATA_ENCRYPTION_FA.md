# ADR-001 — حفاظت داده و پشتیبان رمزگذاری‌شده

وضعیت: **پذیرفته‌شده برای پشتیبان؛ حفاظت پایگاه فعال هنوز باز است**
تاریخ: ۱۴۰۵/۰۸/۱۳

## زمینه و معیارها

نسخه تجاری باید محرمانگی و یکپارچگی پشتیبان، بازیابی بدون بازنویسی، کار آفلاین و امکان ساخت Windows را فراهم کند. ورود برنامه به‌تنهایی از کپی آفلاین SQLite محافظت نمی‌کند.

## گزینه‌ها

۱. رمزگذاری دست‌ساز یا XOR: رد شد؛ فاقد امنیت و احراز اصالت.
۲. ZIP دارای رمز قدیمی: رد شد؛ الگوریتم و مدیریت خطای نامناسب.
۳. AES-256-GCM و Scrypt با کتابخانه `cryptography`: برای پشتیبان پذیرفته شد.
۴. SQLCipher برای پایگاه فعال: از نظر فنی مناسب، اما binding و بسته‌بندی Windows، مهاجرت اتمیک، بازیابی کلید و مجوز/پشتیبانی آن هنوز باید نمونه‌سازی و پذیرش شود.
۵. BitLocker/EFS/ACL: کنترل تکمیلی لازم، ولی به‌تنهایی قابل حمل و تحت کنترل برنامه نیست.

## تصمیم

- قالب نسخه‌دار `SABAENC1` با AES-256-GCM، nonce تصادفی ۹۶ بیتی، کلید ۲۵۶ بیتی و Scrypt (`N=32768,r=8,p=1`) استفاده می‌شود.
- سرآیند به‌عنوان AAD احراز اصالت می‌شود؛ tag و رسید SHA-256 دست‌کاری را آشکار می‌کنند.
- عبارت بازیابی حداقل ۱۲ نویسه است، ذخیره یا log نمی‌شود و گم‌شدن آن به معنی عدم امکان بازیابی است.
- بازیابی فقط روی مسیر جدید انجام می‌شود و پس از رمزگشایی، integrity و foreign key SQLite کنترل می‌گردد.
- snapshot متن‌باز فقط در پوشه موقت زمان رمزگذاری ایجاد و پاک می‌شود.

## وابستگی و مجوز

`cryptography==50.0.0` از PyPI رسمی pin شده است. پروژه cryptography تحت Apache-2.0 یا BSD-3-Clause عرضه می‌شود. بررسی advisory و نگهداری دوره‌ای dependency همچنان جزو gate انتشار است.

## پیامد و محدودیت

این تصمیم پشتیبان را رمزگذاری می‌کند، نه فایل SQLite فعال را. تا انتخاب و آزمون SQLCipher یا کنترل معادل، BitLocker و ACL ویندوز الزامی و gate «رمزگذاری داده در حالت سکون» باز است. آزمون بازیابی روی ماشین مستقل و مدیریت سازمانی عبارت بازیابی نیز لازم است.
